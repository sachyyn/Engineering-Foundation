# Local setup, delivery and recovery

## Local-only service definitions

`compose.yaml` defines PostgreSQL 18, Mailpit and optional PHP 8.4 tooling. No service was
started in this trial. Docker/PHP are unavailable, so image build, Compose semantics and
actual connectivity are NOT verified. Images use major/minor development tags; this is
not a reproducible production image definition. Record verified image digests before release.

On a developer machine with Docker already installed:

```sh
docker compose config --quiet
docker compose up -d postgres mailpit
docker compose ps
```

Ports bind only 127.0.0.1; PostgreSQL uses trust authentication solely for disposable local
synthetic data, and container-network peers can access it. Never reuse this configuration
on a shared/production host. Mailpit never sends real outbound mail. No credentials are
provided or generated by the foundation. Named volume persists local data; ordinary stop
uses `docker compose down`. Removing volumes destroys that data and needs explicit intent.

Before application DB tests, provision distinct local `ledgerdesk_migrator` owner and
`ledgerdesk_app` runtime roles and separate development/test databases. Runtime has no
superuser/BYPASSRLS/CREATEROLE/DDL/TRUNCATE. Grant only needed DML and sequence rights.
Use the bootstrap admin only to create roles/databases, not for tests or application.
Role/bootstrap migrations belong to a later authorized application setup; no product SQL
or migrations are shipped here. Tests must verify role attributes instead of trusting names.

Optional PHP tool image definition is `tooling/php/Dockerfile`; validate/build locally
before use. It installs PHP extensions for Doctrine/Symfony/test support, then Composer.
Build-time apt/image downloads are explicit, not executed here. Keep Composer home/cache
under repository `.cache` and review generated ownership when bind-mounting. Native PHP
8.4 with matching extensions is equally acceptable. Do not install PHP globally for this trial.
Node checks run natively on 22.23.1 with npm 10.9.8; no global install or hook activation.

## Environment contract for future application setup

Runtime requires database/session/limiter storage connection, trusted public HTTPS origin,
trusted hosts/proxies, and SMTP transport configuration. Development uses local PostgreSQL
and Mailpit; tests use a separate disposable database and captured mail. Production values
are external secret/configuration inputs and are not configured here. Do not commit `.env`
or real values. When authoring a future `.env.example`, use non-secret placeholders and
document required values without claiming they exist. Never expose backend values via
Vite's client environment prefix.

## Provider-independent release procedure

No CD workflow or cloud resources are created. When a provider and production activation
are approved, implement a pipeline with these ordered requirements:

1. Identify source revision and lockfiles; build frontend assets plus backend dependencies
   under pinned Node/PHP environments. Run all quality suites with real PostgreSQL. Produce
   an immutable artifact with checksums and dependency inventory/license review. Do not
   rebuild different artifacts per environment or include development mail capture/config.
2. Verify previous artifact, migration plan, tested restoration path and required production
   environment configuration. Require explicit production approval and protected identity.
3. Serialize deploys per environment. Run expand migrations once using a separate migration
   identity; do not let each web instance migrate on startup. Backfills are bounded/restartable.
4. Promote the tested artifact; restart/drain workers so old message handlers do not outlive
   schema compatibility. Set worker memory/time limits and supervise restarts.
5. Verify liveness (process only), readiness (DB/required dependencies, no sensitive output),
   login and a synthetic tenant-scoped read/write smoke flow. No real customer data in probes.
6. On failure stop rollout. Revert application only if compatible with the expanded schema;
   prefer forward fix for irreversible data changes. Never blindly run a generated down migration.
7. Contract old schema only after all app/worker versions have moved and recovery review passes.

## Observability, failure and recovery

Use structured logs with request/job ID, operation, status, duration and safe error code.
Keep raw payloads, customer identity, money details, credentials and reset links out of logs.
Audit issuance/cancellation/user-management with actor, tenant, target, action and timestamp;
restrict access and define retention before launch. Alert on sustained server errors,
readiness failures, mail dead-letter growth and backup/restore failures. The small team's
lead must name the operational owner and escalation channel; no fictitious on-call exists.

For reset mail failures inspect safe job metadata, transport availability and attempt count.
Do not copy tokens/mail bodies into tickets. Retry boundedly; old pending token may be invalidated
by retry. If exhausted, resolve transport then requeue using current account state, or instruct
user to request a new link. Replay tests must establish tenant context and no stale EntityManager.

Backups require a provider-specific encrypted backup and access policy, monitoring and a tested
restore path. Choose dump/PITR based on approved RPO/RTO, not convenience. Restore to isolated
infrastructure, verify schema/migration identity, row counts/constraints, cross-tenant denial,
and essential application flow. Record observed elapsed time, last recoverable transaction and
owner; compare against objectives. Repeat before risky migrations and on the agreed schedule.
No production backup, restore, alert or recovery guarantee has been verified here.

## Launch gates and maintenance

The lead must close these before launch: legal invoice issuance/cancellation policy, retention
and erasure policy (including queue/audit/backups), residency, recovery objectives, production
host/email service, secret/identity management, monitoring owner and restore drill. USD-only/no-tax
is product scope, not a regulatory guarantee. Production issuance must remain disabled until
its legal policy is approved; draft/customer development may proceed under these rules.

Review dependency advisories in each PR and before release. Run npm/Composer audits, review
licenses and lock diffs, inspect install scripts, update supported patch releases with tests.
No automated dependency schedule or policy caretaker was installed. Review Node 22 support
before its end of support and PHP/Symfony/PostgreSQL support at release planning. Explicit
foundation reassessment is triggered by auth/tenant/role/currency/tax/provider or runtime changes.
